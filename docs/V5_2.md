# v5.2（データを育てる）

v5.2 の機能は、このフォルダに適用済みです（初回に事前集計が自動で作られます）。

## 既存の試合データは「そのまま使う」（リセットしない）
- 旧データにも **チャンピオン・ロール・勝敗・KDA・ダメージなど** は入っているため、事前集計・スコア基準の材料としてそのまま使えます。
- 旧データに無いのは **バン・オブジェクト・帯** だけです。これらは「入っている試合だけ」で数えます（バン率の分母は、バン情報のある試合の数）。
- 旧データの帯は `UNKNOWN`（帯不明）になり、「帯: すべて」でのみ集計されます。「マスター以上」などの絞り込みには、v5.2 以降にクローラーが集めた試合だけが入ります。
- 保存件数の上限（`MAX_MATCHES`、既定 20000）を超えると古い試合から消えるため、旧データは自然に入れ替わります。**集計は試合を消しても減りません。**
- 初回だけ、保存済みの試合から事前集計を作ります（`/champions` を開いたとき、または試合を保存したときに自動。2万試合で数十秒が目安）。先に済ませたいときは `npm run agg:rebuild`。

## 追加・変更されたもの
| 機能 | 内容 |
|---|---|
| 帯別の統計 | クローラーが「マスター以上 / ダイヤ / エメラルド」の順位表から起点を取り、各試合に起点の帯を保存。画面で「すべて / マスター以上 / ダイヤ以上 / エメラルド以上」を選べます。**帯は起点プレイヤーのランク帯による目安**で、試合の平均ランクではありません |
| 保存項目の追加 | バン、チームのキル数、ドラゴン・バロン・ヘラルド・タワーなど（取得済みデータの保存漏れを直しただけで、API は増えません） |
| 事前集計 | 試合を **新しく保存できたときだけ** 「パッチ × 帯 × ロール × チャンピオン」の集計へ加算。表示は集計を読むだけなので、試合が増えても速いままです |
| ティアリスト | `/tierlist`。補正勝率・ピック率・バン率で S/A/B/C、前パッチとの差。試合数が少ないチャンピオンは「データ不足」 |
| オブジェクトと勝率 | ティアリストの下に「ドラゴン3体以上 / バロン / ヘラルド / ファーストブラッド / ファーストタワーのときの勝率」 |
| 過去の試合の取り込み | プロフィール上部の「過去の試合を読み込む」（100 / 200 / 300 試合）。裏で少しずつ取得し、進捗を表示。他の操作を優先するため優先度は low |
| スコアの精度 | 集計が貯まると、「ロール × チャンピオン」の平均を基準にスコアを付けます（下記） |

## ティアの決め方
- 補正勝率 = （勝ち数 + 10）÷（試合数 + 20）。勝率50%の仮想試合を20回足して、試合数が少ないときの極端な勝率を抑えます。
- 総合点 = 補正勝率 − 50 + ピック率 × 0.08 + バン率 × 0.04
- 最低試合数（既定 30、ロール指定時は 15）以上のチャンピオンを総合点で並べ、**上位10% = S、35%まで = A、75%まで = B、残り = C**。固定の閾値ではなく、その条件の中での相対順位です。比べる相手が5体未満のときはティアを付けません。
- 標本はこのサイトの DB に貯まった試合だけで、OP.GG のような全体統計ではありません。

## スコアの基準
- 基準の試合数が足りる参加者（チャンピオン × ロールで30試合以上、足りなければロール全体で200試合以上）は、基準との比較で採点します。重みは KDA 30% / ダメージ 25% / キル関与 15% / ゴールド 10% / 視界 10% / CS 10%（ダメージ・ゴールド・視界・CS は1分あたり）。
- 足りない参加者は、その人だけ従来の試合内の相対評価に戻ります（重みは従来のまま）。
- 基準は **ソロランク（キュー420）の全パッチ・全帯の平均** です。ARAM などロールのない試合は従来の採点です。
- 同じ試合の中で2つの方式が混ざることがあります。点数の基準が変わるため、v5.1 までのスコアと並べて比べないでください。

## 追加の設定（すべて任意。`.env` に書かなければ既定値）
```
# クローラーが起点にする帯（MASTER_PLUS,DIAMOND,EMERALD,PLATINUM,GOLD,SILVER）
# CRAWLER_BANDS=MASTER_PLUS,DIAMOND,EMERALD
# 1回の起点取得で、帯ごとに使う人数
# CRAWLER_SEEDS_PER_BAND=150
# ティアリストの最低試合数（ロール指定時は半分）
# TIER_MIN_GAMES=30
# スコア基準に必要な最低試合数（チャンピオン × ロール / ロール全体）
# BASELINE_MIN_CHAMP=30
# BASELINE_MIN_ROLE=200
```

## API の消費
- 帯別の起点取得: 帯ごとに順位表を数回（マスター以上は3回、それ以外は4回）。起点の入れ替えのたびに実行
- 過去の試合の取り込み: 試合1件につき1回（300試合で約300回。優先度 low のため、検索など他の操作を邪魔しません）
- それ以外（保存項目の追加・事前集計・ティアリスト・スコア基準）: 追加の API 呼び出しなし

## クローラーの動きの変更
v5.1 までは試合の参加者を新しい起点として広げていましたが、**v5.2 では広げません**。広げると帯のラベルが混ざるためです。かわりに起点を定期的に取り直します（順位表のランダムなページから）。

## v5.1 の不具合修正（適用済み）
プロフィールの進捗確認（約0.8秒おき = 1分に約75回）が `/api/sync` のIP制限（1分20回）に引っかかり、同期が長引くと「状態を確認できませんでした」になる問題がありました。上限を 1分120回に引き上げています。

## 既知の制限
- 実際の Express・EJS・MongoDB・Riot API を使った通し検証は、この環境ではできていません（npm が使えないため）。初回は `npm test` のあと、`/tierlist` と `/champions`、プロフィールの「過去の試合を読み込む」を順に試してください。
- 事前集計は加算式のため、保存の途中でプロセスが落ちるなどすると、ごくわずかにずれることがあります。そのときは `npm run agg:rebuild`。
- 既存の「チャンピオン詳細」ページ（`/champion/名前`）は、これまでどおり保存済みの試合を直接集計します（今回は変更していません）。
- 保存できる件数の上限を超えて古い試合が消えても、事前集計は減りません。「集計済み N 試合」は、DB に残っている試合数より多くなることがあります。
